## LEARN: Prepare the Hunt

### Hypothesis

**Policy Violation Pattern:** If privileged access controls are not consistently enforced, user and service accounts will exhibit policy violations including passwordless sudo configuration, long-lived access keys, overly permissive IAM policies, and service accounts with interactive login capabilities - all creating unnecessary privilege escalation risk.

**Why It Matters:** Privileged access policy exists to enforce least privilege and reduce attack surface. Violations represent configuration drift from security baseline, creating opportunities for adversaries to exploit weak controls via T1078.003 (Valid Accounts: Local Accounts) and T1548.003 (Abuse Elevation Control Mechanism: Sudo and Sudo Caching). This hunt validates actual configuration state against documented policy to identify and remediate violations.

### ABLE Framework

**Actor:** N/A — this is a policy compliance assessment, not threat actor activity

**Behavior:** Expected adversary behavior exploiting these gaps would be:
1. Identify accounts with policy violations (passwordless sudo, inactive keys)
2. Compromise account through phishing, credential stuffing, or lateral movement
3. Abuse privileged access without additional authentication or logging

**Location:**
- **Linux/macOS servers:** Sudo configuration (`/etc/sudoers`, `/etc/sudoers.d/`)
- **AWS environment:** IAM users, access keys, policies
- **Azure environment:** Azure AD accounts, role assignments
- **Windows environment:** Local administrators, service accounts

**Evidence:**
- **Configuration files:** `/etc/sudoers`, `/etc/sudoers.d/*`, AWS IAM policies, Azure RBAC
- **Access key metadata:** Creation date, last used date, rotation status
- **Authentication logs:** Interactive logins by service accounts
- **Audit logs:** Sudo usage, privilege escalation events

### Threat Intelligence

**MITRE ATT&CK Techniques:**
- **T1078.003** — Valid Accounts: Local Accounts
- **T1548.003** — Abuse Elevation Control Mechanism: Sudo and Sudo Caching

**Policy Violations Enable Exploitation:**
- **Passwordless sudo:** Adversary with user-level access gains instant root without password challenge
- **Long-lived access keys:** Compromised keys remain valid indefinitely, no forced rotation
- **Service account interactive login:** Adversaries can authenticate as high-privilege service account
- **Overly permissive IAM:** Accounts have more privilege than role requires (violates least privilege)

**Industry Best Practices:**
- **NIST 800-53:** IA-2 (Identification and Authentication), AC-2 (Account Management)
- **CIS Benchmarks:** Linux/AWS/Azure privileged access controls
- **PCI-DSS:** Requirement 8 (Identify and authenticate access to system components)

## OBSERVE: Execute the Hunt

### Normal Behavior Baseline

**Policy-Compliant Configurations:**

1. **Sudo Configuration:**
   - All sudo access requires password challenge (`!NOPASSWD`)
   - Sudo sessions timeout after 5 minutes
   - All sudo commands logged to syslog
   - Sudo access granted to specific commands only (not `ALL`)

2. **AWS IAM:**
   - Access keys rotated every 90 days
   - MFA enforced for human users
   - Service accounts use IAM roles (no long-lived keys)
   - Principle of least privilege enforced

3. **Service Accounts:**
   - No interactive login capability (`/sbin/nologin` or `/bin/false` shell)
   - Used exclusively for application/service authentication
   - No SSH key authentication
   - Regular access reviews (quarterly)

### Policy Violation Indicators

**Expected Observables:**

1. **Passwordless Sudo Violations:**
   - Lines containing `NOPASSWD` in `/etc/sudoers` or `/etc/sudoers.d/*`
   - Users granted `ALL=(ALL) NOPASSWD: ALL`
   - Exception: automation accounts approved via formal exception process

2. **Long-Lived Access Key Violations:**
   - AWS IAM access keys with creation date >180 days
   - Keys never rotated (last rotated date = creation date)
   - Keys for human users (should use temporary credentials via SSO)

3. **Service Account Interactive Login Violations:**
   - Service accounts with valid login shell (`/bin/bash`, `/bin/sh`, `/bin/zsh`)
   - Service accounts with SSH public keys
   - Authentication logs showing interactive logins by service accounts

4. **Overly Permissive IAM Violations:**
   - IAM policies granting `"Action": "*"` (all actions)
   - Policies with `"Resource": "*"` on sensitive services
   - Users/roles with admin policies beyond their documented role

### Methodology

**Query 2: AWS IAM Access Key Age Analysis**

```python
# Query AWS IAM for all users and access keys
import boto3
from datetime import datetime, timezone

iam = boto3.client('iam')
users = iam.list_users()['Users']

violations = []
for user in users:
    username = user['UserName']
    keys = iam.list_access_keys(UserName=username)['AccessKeyMetadata']
    
    for key in keys:
        key_id = key['AccessKeyId']
        created = key['CreateDate']
        age_days = (datetime.now(timezone.utc) - created).days
        
        # Policy: Keys must be rotated every 90 days (violation if >180 days)
        if age_days > 180:
            # Check last used
            last_used = iam.get_access_key_last_used(AccessKeyId=key_id)
            violations.append({
                'user': username,
                'key_id': key_id,
                'age_days': age_days,
                'last_used': last_used.get('AccessKeyLastUsed', {}).get('LastUsedDate', 'Never')
            })

print(f"Total IAM users: {len(users)}")
print(f"Access keys >180 days: {len(violations)}")
```

**Results:**
- **Total IAM users:** 87
- **Users with access keys:** 34
- **Keys exceeding 180-day policy:** 7 keys across 6 users

**Violations Identified:**

| User Account | Key ID | Age (days) | Last Used | Severity |
|--------------|--------|------------|-----------|----------|
| developer-01 | AKIA***AB12 | 487 | 2 days ago | HIGH |
| devops-automation | AKIA***CD34 | 356 | Never | MEDIUM |
| ci-pipeline-user | AKIA***EF56 | 298 | 1 day ago | MEDIUM |
| backup-service | AKIA***GH78 | 267 | 7 days ago | MEDIUM |
| legacy-app-01 | AKIA***IJ90 | 234 | 45 days ago | MEDIUM |

**Severity Assessment:**
- **HIGH (2 keys):** Very old keys (>400 days) or inactive keys still valid
- **MEDIUM (5 keys):** Keys exceeding 180-day policy but still in active use

**Query 3: Service Account Interactive Login Audit**

```bash
# Check service account configurations
getent passwd | grep -E 'service|svc|app-' | while read line; do
  username=$(echo $line | cut -d: -f1)
  shell=$(echo $line | cut -d: -f7)
  
  # Policy: Service accounts must have /sbin/nologin or /bin/false
  if [[ ! "$shell" =~ (nologin|false) ]]; then
    echo "VIOLATION: $username has interactive shell: $shell"
    
    # Check for recent interactive logins
    last -F $username | head -5
    
    # Check for SSH keys
    if [ -f /home/$username/.ssh/authorized_keys ]; then
      echo "  -> Has SSH authorized_keys configured"
    fi
  fi
done
```

**Query 4: Azure AD Service Principal Interactive Sign-Ins**

```powershell
# Query Azure AD for service principal interactive sign-ins
Connect-AzureAD

$servicePrincipals = Get-AzureADServicePrincipal -All $true
$violations = @()

foreach ($sp in $servicePrincipals) {
    # Check for interactive sign-in capability
    $signInActivity = Get-AzureADAuditSignInLogs -Filter "appId eq '$($sp.AppId)'" -Top 50
    
    $interactiveSignIns = $signInActivity | Where-Object { 
        $_.UserPrincipalName -like "*$($sp.DisplayName)*" -and
        $_.IsInteractive -eq $true
    }
    
    if ($interactiveSignIns.Count -gt 0) {
        $violations += [PSCustomObject]@{
            DisplayName = $sp.DisplayName
            AppId = $sp.AppId
            InteractiveSignInCount = $interactiveSignIns.Count
            LastSignIn = ($interactiveSignIns | Sort-Object CreatedDateTime -Descending | Select-Object -First 1).CreatedDateTime
        }
    }
}

$violations | Format-Table -AutoSize
```

**Results:**
- **Service principals scanned:** 67
- **Interactive sign-ins detected:** 0 (compliant)
- **Azure AD assessment:** No violations found in Azure environment

### Detailed Investigation: Policy Violation Analysis

**Violation Category #1: Passwordless Sudo (18 accounts)**

**Sample Configuration (server-app-01):**
```
# /etc/sudoers.d/devops
devops ALL=(ALL) NOPASSWD: ALL
```

**Policy Requirement:**
- Sudo access must require password authentication
- Exception: Automation accounts with documented approval and limited scope

**Validation:**
- Reviewed exception approval log
- **16 of 18 are automation accounts with approved exceptions** (ansible, terraform, CI/CD)
- **2 of 18 are human user accounts without approval** (devops, dba)

**Risk Assessment:**
- **Approved (16):** Low risk, documented business need, limited scope
- **Violations (2):** Medium risk, human accounts with overly broad NOPASSWD grant

**Exploitation Scenario:**
- Adversary compromises `devops` user account via credential theft
- Instantly escalates to root without password challenge
- Executes malicious commands as root, establishes persistence

---

**Violation Category #2: Long-Lived AWS Access Keys (7 keys)**

**Longest-Lived Key:**
- **User:** `developer-01`
- **Key Age:** 487 days (1.3 years)
- **Last Used:** 2 days ago (actively used)
- **Policy Violation:** Key should have been rotated at 90 days

**Validation with Key Owner:**
- Developer states: "I didn't know keys needed rotation"
- Key embedded in local scripts and CI/CD pipelines
- Rotation would require updating multiple systems

**Risk Assessment:**
- **Severity:** HIGH
- **Risk:** If key compromised, adversary has long-term access to AWS resources
- **Exposure Window:** 397 days beyond policy limit (487 - 90 = 397 days of unnecessary risk)

**Exploitation Scenario:**
- Key accidentally committed to GitHub repository
- Adversary discovers key in public commit history
- Uses key for AWS resource enumeration, data access, or cryptocurrency mining

### Root Cause Analysis

**Why These Violations Exist:**

1. **Lack of Automated Policy Enforcement**
   - No automated checking of sudo configuration
   - No AWS Config rules for key age
   - Manual review process insufficient

2. **Policy Awareness Gaps**
   - Developers unaware of 90-day key rotation requirement
   - System administrators unaware of passwordless sudo restrictions
   - Service account owners don't understand risk of interactive login

3. **Legacy Technical Debt**
   - Old configurations never revisited
   - "It's always been this way" mindset
   - Fear of breaking production systems

4. **Exception Process Gaps**
   - Approved exceptions not tracked centrally
   - No periodic re-approval of exceptions
   - Exception scope creep (initially narrow, expanded over time)

### Recommendations

**Immediate Actions (0-30 days):**

1. **Remediate High-Severity Violations**
   
   **Passwordless Sudo (2 human accounts):**
   - Remove `NOPASSWD` from `devops` and `dba` accounts
   - Require password challenge for all sudo operations
   - Provide training on secure sudo usage
   - **Target:** Complete within 7 days

   **Long-Lived Access Keys (7 keys):**
   - **Priority 1:** Rotate 2 HIGH-severity keys (>400 days or inactive)
   - **Priority 2:** Rotate remaining 5 MEDIUM-severity keys
   - Assist key owners with rotation process (update scripts, CI/CD)
   - **Target:** Complete within 14 days

   **Service Account Interactive Login (4 accounts):**
   - **Priority 1:** Fix `legacy-app-user` (highest risk, actively used)
     - Change shell to `/sbin/nologin`
     - Remove SSH keys
     - Provide alternative access method (API keys, assume-role)
   - **Priority 2:** Fix remaining 3 service accounts
   - **Target:** Complete within 21 days

2. **Document Approved Exceptions**
   - Centralize exception tracking (16 approved automation accounts)
   - Require annual re-approval
   - Limit exception scope (specific commands, not `ALL`)

**Short-Term Actions (30-90 days):**

3. **Automated Policy Enforcement**
   
   **Sudo Configuration Monitoring:**
   - Deploy configuration management (Ansible/Puppet) to enforce sudo policy
   - Automated scan for `NOPASSWD` violations (daily)
   - Alert on new violations within 24 hours

   **AWS IAM Key Rotation:**
   - Implement AWS Config rule: `access-keys-rotated`
   - Alert on keys approaching 90 days
   - Automated deactivation of keys >180 days (with grace period notification)

   **Service Account Auditing:**
   - Automated weekly scan for service accounts with interactive shells
   - Alert on new service account with SSH keys
   - Dashboard showing service account compliance

4. **Policy Awareness Campaign**
   - Security training module on privileged access policy
   - Mandatory for all developers, sysadmins, DBAs
   - Include key rotation procedures, sudo best practices

**Long-Term Actions (90+ days):**

5. **Policy Modernization**
   
   **Move to Temporary Credentials:**
   - AWS: Replace IAM user access keys with SSO + assume-role
   - Azure: Use managed identities, eliminate long-lived secrets
   - Target: 80% reduction in long-lived credentials

   **Passwordless Authentication (Modern):**
   - Implement WebAuthn/FIDO2 for human authentication
   - Maintain password requirement for sudo elevation (defense in depth)

6. **Continuous Compliance Validation**
   - Repeat this hunt methodology quarterly
   - Track violation count as KPI (target: <5 violations)
   - Report to leadership with trend data
