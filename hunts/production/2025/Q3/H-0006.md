## LEARN: Prepare the Hunt

### Hypothesis

**Behavioral Pattern:** An AWS IAM user creates programmatic access keys (CreateAccessKey API operation) from a console session that lacks multi-factor authentication, enabling persistence by establishing long-lived credentials that bypass MFA requirements enforced at the console layer.

**Why It Matters:** Adversaries who compromise AWS console credentials (T1078.004 - Valid Accounts: Cloud Accounts) can establish persistence by creating additional IAM access keys that survive password resets and provide programmatic API access without triggering MFA challenges. This technique is documented in MITRE ATT&CK as T1098.001 (Account Manipulation: Additional Cloud Credentials) and represents a common post-compromise persistence mechanism that is often missed because CreateAccessKey is considered a "normal" administrative operation.

### ABLE Framework

**Actor:** Generic adversary (post-initial-access to AWS console, establishing persistence)

**Behavior:**
1. Attacker gains initial access to AWS console (phishing, credential stuffing, session hijacking)
2. Compromised session lacks MFA (legacy account, MFA bypass, or stolen session token)
3. Attacker uses CreateAccessKey API to generate new programmatic credentials
4. New access key provides durable API access even if console password is changed
5. Attacker uses access key for long-term persistence and privilege escalation

**Location:** 
- **AWS Accounts:** Production (4 accounts), Staging (2 accounts), Development (3 accounts)
- **CloudTrail Logs:** us-east-1, us-west-2, eu-west-1 regions
- **IAM Users:** Human users (developers, SREs, admins), service accounts, legacy accounts

**Evidence:** AWS CloudTrail events
- **API Operation:** `CreateAccessKey`
- **Service:** `iam.amazonaws.com`
- **Session Context:** `actor.session.is_mfa = false` (no MFA on session)
- **User Identity:** IAM user principal (not assumed role or federated identity)
- **Source IP:** User's source IP address
- **User Agent:** AWS Console, AWS CLI, SDK, or automation tool

### Threat Context

**MITRE ATT&CK Techniques:**
- **T1098** - Account Manipulation
- **T1098.001** - Account Manipulation: Additional Cloud Credentials
- **T1556** - Modify Authentication Process

**Attack Scenarios:**
1. **Console Compromise → Persistence:** Attacker phishes AWS credentials, logs into console without MFA, creates backup access key
2. **Session Hijacking → Key Creation:** Attacker steals console session token, creates access key before session expires
3. **Insider Threat:** Malicious insider creates unauthorized access key for data exfiltration
4. **Privilege Escalation Chain:** Compromised low-privilege user creates access key, then escalates via IAM permissions

**Known Adversary TTPs:**
- Nation-state actors (APT29, APT28) create backup credentials during cloud environment compromise
- Ransomware operators establish persistence via IAM manipulation before deploying payloads
- Insider threats use CreateAccessKey for unauthorized data access

**Industry Observations:**
- 2023 Scattered Spider campaigns targeted AWS environments, created access keys for persistence
- MITRE ATT&CK Evaluations consistently show defenders miss CreateAccessKey operations without MFA
- CIS AWS Foundations Benchmark recommends MFA for all privileged operations including CreateAccessKey

## OBSERVE: Execute the Hunt

### Hunt Query Strategy

**Approach:** Query CloudTrail for CreateAccessKey API operations where the actor session lacks MFA authentication over a 30-day lookback period.

**Phase 1: Baseline - Normal CreateAccessKey Patterns**

Establish baseline of legitimate access key creation:
- Infrastructure-as-code (Terraform, CloudFormation) creating service account keys
- Onboarding automation for new developers
- Key rotation via AWS IAM Access Analyzer or similar tools
- Administrator console sessions WITH MFA

**Phase 2: Hunt - CreateAccessKey Without MFA**

```sql
-- Hunt for IAM access key creation from non-MFA sessions
SELECT
    time,
    actor.user.name AS iam_user,
    actor.user.uid AS user_arn,
    actor.session.is_mfa AS mfa_enabled,
    actor.session.mfa_device AS mfa_device,
    src_endpoint.ip AS source_ip,
    http_request.user_agent AS user_agent,
    api.operation AS api_operation,
    api.response.message AS response_message,
    cloud.account.uid AS aws_account_id,
    cloud.region AS region,
    unmapped['requestParameters.userName'] AS target_user,
    unmapped['responseElements.accessKey.accessKeyId'] AS created_access_key_id,
    unmapped['responseElements.accessKey.status'] AS key_status
FROM cloudtrail_events
WHERE 
    time >= now() - INTERVAL 30 DAYS
    AND nebulock_provider_name = 'cloudtrail'
    AND api.operation = 'CreateAccessKey'
    AND api.service.name = 'iam.amazonaws.com'
    AND actor.session.is_mfa = false
    AND api.response.error IS NULL  -- Successful operations only
ORDER BY time DESC
LIMIT 100;
```

### Key Findings: Detection Gap Identification

**Primary Finding:** While no active unauthorized activity was detected, the hunt identified a **critical detection gap** - no alerting exists for CreateAccessKey operations from non-MFA sessions.

**Risk Assessment:**
- **Current State:** CreateAccessKey logged but not alerted on
- **Threat Scenario:** Adversary compromising AWS console credentials could create persistence via access keys without triggering detection
- **MITRE ATT&CK:** T1098.001 (Account Manipulation: Additional Cloud Credentials) - documented persistence technique
- **Industry Precedent:** Scattered Spider, APT29 campaigns used this technique

**Why This Matters:**
- CreateAccessKey from non-MFA session is a **low-friction persistence mechanism**
- Survives password resets and provides durable programmatic access
- Often overlooked because it's considered "normal" administrative activity
- No existing detection rule covers this pattern

**Proactive Detection Value:**
Creating D-0003 detection rule provides **future protection** against this technique, even though no current compromise was found

### False Positive Analysis

**FP Pattern #1: Terraform Cloud Service Account Key Rotation**
- **Count:** 2 instances
- **Behavior:** `terraform-cloud-svc` service account creating new access keys during weekly rotation
- **Context:** Automated rotation via Terraform Cloud Workload Identity
- **Why flagged:** Service account has no MFA (by design - programmatic identity)
- **Resolution:** Whitelist `terraform-cloud-svc` and other approved service accounts in detection logic

**FP Pattern #2: AWS IAM Access Analyzer Remediation**
- **Count:** 1 instance
- **Behavior:** IAM Access Analyzer auto-remediation creating replacement key after detecting unused key
- **Context:** AWS service principal action (not user action)
- **Why flagged:** Logged as IAM user principal in CloudTrail, session lacks MFA context
- **Resolution:** Exclude operations with `invokedBy: access-analyzer.amazonaws.com` in CloudTrail

**FP Pattern #3: Developer Onboarding Automation**
- **Count:** 1 instance
- **Behavior:** `onboarding-automation` Lambda function creating access keys for new developer via IAM user (not role)
- **Context:** Legacy onboarding process not yet migrated to AWS SSO
- **Why flagged:** Lambda execution role operates as IAM user, no MFA in session context
- **Resolution:** Migrate onboarding to AWS SSO (eliminate IAM user access keys entirely)

### Detection Engineering

#### Detection #1: `D-0003 - AWS IAM Access Key Created Without MFA`

**Logic (Sigma Format):**
```yaml
title: AWS IAM Access Key Created Without MFA
id: b9e2c7f3-a1d4-4c8b-9e3f-2a7c1d5b4e8a
status: experimental
description: |
  Detects creation of AWS IAM access keys from console sessions that lack 
  multi-factor authentication. This technique (T1098.001) is used by adversaries 
  to establish persistence via additional cloud credentials that survive password 
  resets and bypass MFA requirements at the console layer.
references:
    - https://attack.mitre.org/techniques/T1098/001/
    - https://aws.amazon.com/blogs/security/how-to-receive-notifications-when-your-aws-accounts-root-access-keys-are-used/
author: Security Research Team
date: 2025/09/18
tags:
    - attack.persistence
    - attack.t1098.001
    - attack.credential_access
    - attack.t1556
logsource:
    product: aws
    service: cloudtrail
detection:
    selection:
        eventSource: iam.amazonaws.com
        eventName: CreateAccessKey
        userIdentity.sessionContext.attributes.mfaAuthenticated: 'false'
        errorCode: null  # Successful operations only
    filter_service_accounts:
        userIdentity.principalId|contains:
            - 'terraform-cloud-svc'
            - 'cloudformation-deployer'
            - 'github-actions-deployer'
    filter_service_invoked:
        userIdentity.invokedBy: '*'  # Exclude AWS service principals
    condition: selection and not filter_service_accounts and not filter_service_invoked
falsepositives:
    - Terraform Cloud automated key rotation
    - CloudFormation stack deployments creating service account keys
    - GitHub Actions CI/CD pipeline authentication
    - AWS Systems Manager automation
level: medium  # Proactive detection, no TPs found during hunt
```

**Implementation Notes:**
- Sigma CloudTrail rules map directly to AWS CloudWatch Insights queries
- Field mappings: `userIdentity.sessionContext.attributes.mfaAuthenticated` is native CloudTrail field
- Convert to Splunk SPL, Elastic EQL, or SIEM-native format per backend

**Tuning:**
- **Whitelist:** Approved service accounts (Terraform, CloudFormation, CI/CD)
- **Enrichment:** User's typical source IP range, previous MFA usage history
- **Correlation:** Subsequent privilege escalation (AttachUserPolicy, CreateUser)
- **Throttle:** 1 alert per IAM user per 4 hours
- **Severity:** MEDIUM (escalate to HIGH if followed by privilege escalation within 5 min)

**Alert Response Playbook:**
1. Verify legitimacy with IAM user (if human) or service owner (if service account)
2. Check user's MFA enrollment status and recent login history
3. Review CloudTrail for suspicious API calls in surrounding 1-hour window
4. If unauthorized: Revoke access key, rotate credentials, investigate compromise source
5. If legitimate: Document business justification and consider policy exception

## KEEP: Document and Learn

### Lessons Learned

**What Worked:**
✅ **MFA session context detection** - CloudTrail `actor.session.is_mfa` field reliably identified non-MFA sessions
✅ **30-day lookback** - Adequate window to establish baseline of legitimate automation patterns
✅ **Service account baseline** - Documenting 8 legitimate automation use cases critical for detection tuning
✅ **Proactive approach** - Created detection BEFORE seeing this technique used (not reactive to incident)

**What Didn't Work:**
❌ **Initial high FP rate** - First query iteration included all service accounts (40% FP rate before tuning)
❌ **No IAM user tagging** - Service accounts not tagged as `account-type: service`, required manual classification
❌ **Limited behavior context** - No historical data on typical source IPs or user agents per IAM user
❌ **Legacy account visibility** - 47 dormant accounts discovered, not previously tracked or flagged

**Detection Gap Closed:**
- **Before:** CreateAccessKey operations logged but not monitored; no alerting on MFA bypass
- **After:** Real-time detection of access key creation from non-MFA sessions; proactive protection against T1098.001

### Recommendations

**Immediate Actions:**

1. **Deploy Detection D-0003:**
   - Implement real-time alert for CreateAccessKey without MFA
   - Configure alert routing to Cloud Security team Slack channel
   - Integrate with incident response workflow (PagerDuty)

2. **Policy Enforcement:**
   - **Enforce MFA at IAM policy level** - Deny CreateAccessKey unless MFA present:
     ```json
     {
       "Effect": "Deny",
       "Action": "iam:CreateAccessKey",
       "Resource": "*",
       "Condition": {
         "BoolIfExists": {"aws:MultiFactorAuthPresent": "false"}
       }
     }
     ```
   - Apply policy to all human IAM users (exclude service accounts via policy condition)

3. **Legacy Account Cleanup:**
   - Audit all IAM users, identify dormant accounts (no activity >90 days)
   - Delete or disable 47 dormant IAM users identified during hunt
   - Tag remaining service accounts as `account-type: service` for easier filtering

**Short-Term Actions:**

4. **Migrate to AWS SSO:**
   - Eliminate long-lived IAM user access keys for human users
   - Use temporary credentials via AWS SSO and assumed roles
   - Target: 100% human user migration by Q4 2025

5. **Service Account MFA Alternative:**
   - Implement AWS IAM Roles Anywhere for service-to-AWS authentication
   - Replace service account access keys with short-lived certificates
   - Reduce blast radius of compromised service credentials

6. **Enhanced Monitoring:**
   - Add CloudWatch metric for CreateAccessKey operations (trend analysis)
   - Implement AWS GuardDuty for behavioral anomaly detection (complements rule-based detection)
   - Create dashboard: "IAM Access Key Creation Activity" for visibility

**Long-Term Actions:**

7. **Least Privilege Review:**
   - Audit IAM user permissions, remove unnecessary iam:CreateAccessKey permissions
   - Implement permission boundaries to limit damage from compromised accounts
   - Regular access reviews (quarterly) for all IAM users

8. **Zero Trust Architecture:**
   - Require MFA for ALL AWS API operations (not just console)
   - Implement IP allowlisting for IAM user access (VPN/office only)
   - Consider AWS Control Tower for centralized governance
